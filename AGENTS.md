# Architecture rules

- Keep opportunity-stage presentation in the shared `OpportunityStagesStepper` using `IXCard` and the existing advancement callback, so the page and dialog remain consistent without duplicating mutations.- Compute relative renewal/due days with `src/lib/dates/lisbonDays.ts` (Europe/Lisbon calendar days), never hour-based differenceInDays, so 'Hoje/Amanhã' never truncates.
- Decide WhatsApp button state via `src/lib/whatsapp/availability.ts` fed by `useWhatsAppStopSignals` (opt-outs, revoked consents, preferences, fail-closed while loading); it governs assisted communication only, never automatic sends.
- Match WhatsApp opt-outs/consents by `phoneOptOutVariants` (`supabase/functions/_shared/phoneVariants.ts`, mirrored in `src/lib/whatsapp/phoneVariants.ts`, parity-tested) and query only the contact's variants, so client and server agree without exposing the opt-out list.
- Map Stripe subscription state to contracts only via `supabase/functions/_shared/stripeRenewalStatus.ts` and fail the sync result when the contract update errors, so cancellations are never reported as success.
- Read the contact's next task via `fetchContactNextTask` after workspace-instance resolution, with the shared tasks invalidation prefix, so instance changes and task edits cannot leave stale results or hide read failures.
- Public store code must use `src/lib/browser/safeBrowser.ts` for IDs and local/session storage (never bare `crypto.randomUUID`/storage), because older iOS and in-app browsers crashed product pages.
- Store legal pages live under `/store/:slug/*` (e.g. `StoreTermsPage`) and show only configured store data; the CRM `/terms` covers SaaS subscriptions only.
- Store error boundaries must route chunk-load errors to `recoverFromChunkError`, because a plain reload keeps the stale service-worker HTML.
- The PWA service worker must use skipWaiting + clientsClaim + cleanupOutdatedCaches (autoUpdate), because a waiting worker without a visible prompt kept old clients on stale HTML whose chunks were already removed.
- Payment settings routes in `OWNER_ESSENTIAL_ROUTE_KEYS` (MenuVisibilityGuard) stay reachable by direct link for users with `integrations.manage` even when menu overrides hide them, so owners can always configure payments while the menu stays simplified.

- Keep prospecting destinations in the shared route manifest and use `isNavigationRouteActive` for query/anchor matching, so section links highlight the same destination without adding pages or duplicating URLs.
- Show prospecting CRM identity only via `prospecting_identity_check_batch` (`useProspectingIdentityBatch`, small chunked RPCs (10 per call, ≤3 concurrent) per visible page ≤100, workspace in key) and `ProspectingIdentityBadge`, and create prospecting leads only via `prospecting_import_lead_safe`, so lists never fan out per row and no flow bypasses the server-side duplicate recheck.
- Prospecting share content (https link or MP4 in the private `prospecting-videos` bucket, path workspaceId/userId/random.mp4, signed 90-day link, renewed via `ensureFresh` before preparing, never auto-deleted while a link may circulate) lives only in `prospecting_outreach_media` per (workspace, profile, step) via `useOutreachMedia`, is composed with `composeMessageWithLink` (link exactly once) and never feeds identity checks; WhatsApp assisted sends record nothing until «Já enviei» and every «Já enviei» (AIDA, bulk, pending) goes through `confirmOutreachWithReview` → `prospecting_confirm_outreach` (fresh identity re-check, profile+step lock, queue + outreach_step in one transaction; queue has duplicate groups, never add UNIQUE), so opening a link is never counted as sent.
- Commercial sales reps without login live in `sales_reps` (workspace-scoped, assigned via `companies/contacts.sales_rep_id`, contacts inherit the company rep, cross-workspace blocked by trigger) and are chosen only through `SalesRepSelector`, so 'Gestor' (users) and 'Vendedor' (non-users) never mix.
- Hot-table SELECT policies use `workspace_id IN (SELECT get_user_workspace_ids()) OR (SELECT is_super_admin(auth.uid()))` instead of per-row `is_workspace_member(...)`, because the per-row call made PHARLISS invoice reads take ~4.6 s instead of ~10 ms.
- Dashboard invoice cards read all rows via paginated `useDashboardInvoices` (not `useInvoices`), because the API caps a single response at 1000 rows.
- Public Meta store feed prices must match the public B2C base price without an extra tax multiplier, because the storefront and checkout charge that catalogue price.
- Bulk sent-profile conversion uses `importSentProfile` after the outreach gate without prospecting follow-up scheduling, because conversion deliberately ends prospecting and cancels its pending queue.
- FastMatch reputation is maintained by atomic review triggers with a protected rating sum/count; never aggregate RLS-filtered reviews or write reputation from the client.
- EventMap reads only the admin-authorized `read_event_catalog` projection, falling back to the active live Kernel registry when the legacy catalogue is empty, without exposing payload schemas.
- Score new leads against the workspace ICP only via the `lead_icp_score_queue` (statement-level insert trigger wakes `score-leads-icp`, bounded batches, global lease lock, per-workspace pause on 402/403, depth-budgeted chain, hourly backstop), so imports never fan out per row and credit failures stop all work.
- WhatsApp conversations reach the CRM without Z-API only via the extension's explicit «Guardar conversa no CRM» (user token, crm.write, dedupe by external_message_id 'waweb:' hash), never by background reading.
- Official Meta WhatsApp sends go only through `whatsapp-pro-send` → `_shared/whatsappMetaOfficial.ts` when the workspace's active instance is `meta_cloud_api` with matching `metadata.allowed_workspace_id`, because one Meta connection serves a single workspace and must fail closed elsewhere.
- Meta WhatsApp templates are stored in `whatsapp_meta_templates` (+versions/variables/button_actions/events), written only by the `whatsapp-meta-templates` edge function (members read via RLS), with rules in `_shared/metaTemplateRules.ts`; approved/pending templates are locked (duplicate to change) and sends require APPROVED + opt-out/consent checks server-side, because Meta approval is never consent.
- Retainer (avença) hours live in `service_retainers`; projects/tickets link via `retainer_id`, time entries inherit it by trigger (same-workspace guard) and monthly usage/overage is computed only by `src/lib/retainers/retainerUsage.ts` (Lisbon calendar month, no carry-over), so project and support time share one balance; monthly invoices are only drafts built by `buildRetainerInvoiceLines` and deduped by `retainerInvoiceTag` in the notes, never auto-issued.
- Client portal reads projects/tickets/hours only via SECURITY DEFINER RPCs `portal_list_work`/`portal_list_hours` and approves via `portal_review_hours` (client company + client_admin/client_financial role), because client users have no workspace membership; editing an entry resets `client_approval_status` to submitted.
- Client portal mode (services vs store) comes only from `src/lib/clientPortal/portalMode.ts`; services workspaces never render store/cosmetic routes, because agency clients must only see projects, support and hours.
- Services portal allowance summaries use only `portal_retainer_summary` (authenticated client company/workspace, Lisbon month); map its minimal entries through `portalRetainerUsage` to the shared usage calculator, so internal notes and pricing stay private and balances match the CRM.
- Student Journey enrollments keep separate `admin_status`/`pedagogic_status`/`financial_status` (legacy `status`/`payment_status` deprecated), one per profile+cohort unless `duplicate_approved`, completion requires attendance (DB trigger), and money is computed only by `src/lib/studentJourney/enrollmentFinance.ts`; finance tables are gated by `sj_has_any_role`, because commercial, pedagogic and financial states must never overwrite each other.
- The Student Journey profile page is one record with URL-driven tabs (`?tab=`); finance data loads only after `sj_has_any_role` (gestao/financeiro) and the unified timeline is built by `src/lib/studentJourney/timeline.ts`, so the client never fetches finance rows it cannot show.
